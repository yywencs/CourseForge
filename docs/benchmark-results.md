# CourseForge 性能测试记录

本文记录可复现的正式性能测试结果。每轮测试必须保留代码提交、机器拓扑、配置、请求规模、延迟、实际落库吞吐和最终一致性结果，避免只用入口 QPS 代替核心链路能力。

> 架构变更说明：当前选课核心链路为 `Redis Lua → Redis Stream Consumer Group → MySQL`，
> HTTP 在 Lua 原子决策及 Stream 写入成功后返回，不再等待 RabbitMQ Confirm。本文先记录新链路
> 正式复测，再保留 `Redis Lua → RabbitMQ → MySQL` 历史数据用于说明优化过程，两类结果不能
> 直接视为同一实现的多轮波动。

选课容量口径只包含用户请求必须依赖的核心链路，即入口受理和 Stream 异步落库。MySQL 提交后
产生的通知 Outbox、RabbitMQ 投递和站内通知允许异步收敛，不参与选课完成延迟或核心持续吞吐
计算；正式测试仍校验 Outbox、通知数量和 DLQ，确保非关键链路最终没有丢失或重复落库。

### 结论与下一组实验

平均批次已经接近 batch size 100，基线吞吐近似符合“消费者数 × 平均批量 ÷ 单批事务耗时”。下一组实验保持数据规模和 HTTP 并发不变，只调整：

- RabbitMQ publisher pool：16 → 32
- selection result consumer：2 → 4
- prefetch：200 → 400
- batch size 和 batch wait 保持 100、10ms

这样可以判断增加发布并行度和批量落库并行度是否能利用当前剩余的 CPU 与 MySQL 余量。

本轮 20,000 条核心记录落库跨度为 27.851 秒。落库期间 CPU 平均值约为 API 69.38%、MySQL 120.52%、Redis 77.77%、RabbitMQ 107.27%，仍未达到 4 核整机上限。吞吐下降的直接表现是消费者增多后批次填充率下降、事务数增加，并对同一教学班相关数据产生更多并发争用。

## 2026-08-09：WebSocket 多房间场景

WebSocket benchmark 增加 `--rooms`。`--video-id` 表示连续视频 ID 的起点，客户端按序号轮询分配到房间，所有 publisher 使用全局序号在房间间均匀发布。结果使用 schema v2，除全局指标外还记录逐房间发布数、应收/实收、完整率、重复数、协议错误和 10ms 精度的延迟分位数。

测试仍使用三台 4C8G 主机，被压机运行单个 API 实例并将容器 `nofile` 提高到 65535。正式测量均持续 30 秒，使用独立的 ready preview 视频作为房间。

| 场景 | 房间与连接 | 实际发布 | 广播投递 | 完整率 | P50 | P95 | P99 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 单热点房间基线 | 1 × 1000 | 99.66/s | 99,663/s | 100% | 45ms | 70ms | 78ms |
| 5 个高频房间 | 5 × 200 | 343.42/s | 68,685/s | 100% | 53ms | 270ms | 310ms |
| 1000 个低频房间 | 1000 × 5 | 99.66/s | 498.32/s | 100% | 8ms | 13ms | 18ms |

5 个高频房间共完成 10,303 次发布和 2,060,600 次投递，零发布失败、零重复、零协议错误。每个房间完成约 2,060 次发布，逐房间完整率均为 100%，P99 分布为 310～330ms，没有出现房间饥饿。目标发布速率为 500/s，但同步 MySQL 持久化、Redis 发布和 Hub 广播组成的完整发布链路实际稳定在约 343/s。

1000 个低频房间共维持 5,000 条连接，全部建连成功。每个房间在测量窗口收到 2～3 条消息，1,000 个房间均有有效样本且完整率全部为 100%；逐房间 P99 中位数为 10ms、P95 房间为 20ms、最大为 30ms。API 在测试期间内存约 295MiB，说明大量低频房间的主要成本是长连接状态，而不是广播 CPU。

### 瓶颈点

热点场景受单 Hub 事件循环串行扇出以及同步 MySQL、Redis 发布链路限制；房间内连接越多，单条消息的投递成本越高。大量低频房间当前没有触及广播瓶颈，主要容量约束转为文件描述符、连接状态和内存。

当前单实例 Hub 使用一个事件循环串行处理所有房间的广播。多房间分配保持公平，但热点场景的总吞吐仍受单 Hub 和同步发布链路限制；横向扩展 API 实例、让每个实例只扇出本机连接，比继续增加单 Hub 队列更符合现有 Redis Pub/Sub 架构。

## 瓶颈定位与原因

### 选课链路：入口受理与核心落库是两个独立上限

当前接口成功返回代表 Redis Lua 原子决策及 Stream 写入成功，MySQL 由 Consumer Group 异步
批量落库。因此容量需要分别描述：

- **入口受理约为 1,741 QPS。** 与历史 RabbitMQ Confirm 链路最好约 1,158 QPS 相比提升
  50.4%，平均、P95 和 P99 延迟均明显下降。
- **核心落库约为 806 条/秒。** 20,000 条事件在 24.799 秒内完成，共 103 个批次，平均
  每批 194.17 条。批次已经接近 200 的上限，继续单纯扩大 batch size 的收益有限。
- **核心链路可持续容量约为 800 条/秒。** 短时入口可以高于该值，持续高压时差额会进入
  Redis Stream 等待落库，因此不能只引用 1,741 QPS 作为持久化能力。

新链路的单批事务需要写入幂等审计、application、enrollment、计数增量和通知 Outbox，固定
SQL 往返、事务提交、redo 刷盘及同一教学班数据竞争是当前主要成本。通知在事务提交后异步
执行，不属于选课完成的实时依赖；容量分析只要求它最终无丢失、无重复业务记录且 DLQ 为空。

各容器没有耗尽 4 核不等于数据库仍有等比例吞吐余量，事务可能等待锁、日志刷盘或网络往返。
后续应优先记录批事务分段耗时、锁等待、慢 SQL 和 redo/fsync，再决定是否合并 SQL、调整
Outbox 写入方式或改变消费者并发；不应只根据 CPU 余量盲目增加消费者。

### WebSocket：热点扇出受单 Hub 串行模型限制

WebSocket 链路也包含两个不同指标：HTTP 发布 QPS 表示每秒接受多少条弹幕，广播投递 QPS 表示这些弹幕经过扇出后被所有连接接收的总次数。一次向 1,000 人房间发布的成本约等于 1,000 次连接队列投递，不能把两者直接比较。

- **单热点房间的主要瓶颈是扇出。** 单房间 1,000 条连接、约 100 次发布/秒时，单实例稳定完成约 99,663 次投递/秒，完整率 100%、P99 78ms。Hub 由单个事件循环串行处理注册、注销和广播，每条消息还需要遍历该房间的连接并写入各客户端发送队列，因此扇出成本随房间连接数线性增长。
- **多个热点房间仍共享同一个串行 Hub。** 5 个房间虽然没有饥饿，但目标 500 次发布/秒只达到 343.42 次/秒，P99 上升到 310ms。增加房间不会增加 Hub 并行度，反而增加更多广播事件、房间查找和连接快照等固定成本；任一热点广播变慢也会推迟其他房间，形成跨房间的队头阻塞。
- **过载后先表现为延迟和客户端队列积压。** 此前 2,000 连接、100 次发布/秒的探测共应接收 2,740,000 次、实际接收 2,728,575 次，出现 1,198 次 `client_queue_full`，P99 达 7.85s、最大延迟 16.155s。该组只用于定位过载边界，不作为稳定成绩。每个客户端的发送队列有界；当 Hub 投递速度超过连接 write pump 的排空速度时，继续增大队列只会用更多内存换取更高延迟，不能消除瓶颈。
- **大量低频房间当前不是 CPU 瓶颈。** 1,000 个房间、5,000 条连接仍保持 100% 完整率和 18ms P99，说明房间数量本身的影响较小。此场景首先消耗的是文件描述符、连接状态和内存，API 约占 295MiB；容量规划需要持续观察单连接内存和 `nofile`，而不是只看消息吞吐。

热点场景的优化顺序应是：按 `video_id` 对 Hub 分片，使多个事件循环可以并行扇出；或横向扩展 API，让 Redis Pub/Sub 将消息送到各实例，而每个实例只遍历本机连接。发布接口还同步执行视频状态校验、MySQL 持久化、缓存失效和 Redis 发布，这限制了消息发布 QPS；可进一步缓存可播放状态，并在业务允许时将持久化改为可靠异步写入。扩容或改造后仍应同时报告发布 QPS、投递 QPS、P99 和 `client_queue_full`，防止只提高入口速度却把积压转移到连接队列。
