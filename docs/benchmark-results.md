# CourseForge 性能测试记录

本文记录可复现的正式性能测试结果。每轮测试必须保留代码提交、机器拓扑、配置、请求规模、延迟、实际落库吞吐和最终一致性结果，避免只用入口 QPS 代替完整链路能力。

## 2026-08-09：批量消费落库基线

### 环境

| 角色 | 配置 | 私网 IP | 服务 |

| 压测机 | 4C8G | `172.27.2.176` | enrollment benchmark |
| 被压机 | 4C8G | `172.27.2.175` | CourseForge API |
| 基础设施机 | 4C8G | `172.27.2.177` | MySQL 8.4、Redis 7.4、RabbitMQ 4.2 |

- git版本：`1787dbbd4e83f7a7b519395d39739c1096e3a0f3`
- 场景：`selection`
- RabbitMQ publisher pool：16
- selection result consumer：2
- prefetch：200
- batch size：100
- batch wait：10ms
- MySQL 最大连接数：100

### 测试命令

```bash
courseforge-enrollment-benchmark run \
  --url http://172.27.2.175:8080 \
  --scenario selection \
  --users 20000 \
  --concurrency 200 \
  --duration 2m \
  --timeout 5s \
  --verify-timeout 2m \
  --verify-interval 200ms
```

连接信息和 JWT 密钥通过对应参数传入，此处不重复记录凭据。

第二次测试的 MySQL `selection_event.create_time` 显示：

- 20,000 条核心记录在 21.844 秒内落库，平均 `915.58 条/秒`。
- 250ms 轮询曲线计算的边界平均值为 `887.23 条/秒`，1 秒窗口峰值约 `1,618.77 条/秒`。
- 共执行 214 个消费批次，平均每批 93.46 条；20,000 个事件均带有 `consume_batch_id`。
- 测试结束后主队列、重试队列、死信队列的 ready/unacked 均为 0。
- MySQL application/enrollment 均为 20,000，Redis seats 为 0、pending 为 0。

资源采样峰值为 API `108.70%`、MySQL `133.12%`、Redis `96.39%`、RabbitMQ `145.09%`。Docker CPU 百分比以单核为 100%，三台机器均为 4 核，因此本轮没有达到整机 CPU 上限。

### 瓶颈点

入口可以达到约 1,000～1,160 QPS，但异步落库只有约 916 条/秒，持续运行时首先会在 RabbitMQ 消费侧形成积压。结合后续对照实验，主要限制来自 MySQL 批量事务的固定提交和多表写入成本，而不是整机 CPU 或 RabbitMQ publisher 数量不足。

### 结论与下一组实验

平均批次已经接近 batch size 100，基线吞吐近似符合“消费者数 × 平均批量 ÷ 单批事务耗时”。下一组实验保持数据规模和 HTTP 并发不变，只调整：

- RabbitMQ publisher pool：16 → 32
- selection result consumer：2 → 4
- prefetch：200 → 400
- batch size 和 batch wait 保持 100、10ms

这样可以判断增加发布并行度和批量落库并行度是否能利用当前剩余的 CPU 与 MySQL 余量。

## 2026-08-09：4 消费者与 publisher pool 32

本轮保持提交、机器、20,000 用户、200 HTTP 并发、batch size 100 和 batch wait 10ms 不变，只将 publisher pool 调为 32、消费者调为 4、prefetch 调为 400。

| 指标 | 2 消费者基线 | 4 消费者 + publisher 32 | 变化 |
| --- | ---: | ---: | ---: |
| HTTP QPS | 1,157.70 | 768.38 | -33.6% |
| 平均延迟 | 172.15ms | 259.37ms | +50.7% |
| P95 | 235.16ms | 416.92ms | +77.3% |
| P99 | 271.23ms | 553.91ms | +104.2% |
| 核心落库 | 915.58 条/秒 | 718.11 条/秒 | -21.6% |
| 消费批次 | 214 | 250 | +16.8% |
| 平均批次 | 93.46 | 80.00 | -14.4% |
| 最终一致性 | 通过 | 通过 | — |

### 瓶颈点

消费者增加后，同一批消息被拆成更多小事务，并对相同教学班及关联记录产生更强的并发争用。瓶颈从批量写入效率恶化为“批次不满 + MySQL 事务竞争”，因此消费者越多吞吐反而越低。

本轮 20,000 条核心记录落库跨度为 27.851 秒。落库期间 CPU 平均值约为 API 69.38%、MySQL 120.52%、Redis 77.77%、RabbitMQ 107.27%，仍未达到 4 核整机上限。吞吐下降的直接表现是消费者增多后批次填充率下降、事务数增加，并对同一教学班相关数据产生更多并发争用。

因此不保留 4 消费者配置。下一轮将消费者和 prefetch 恢复为 2、200，只保留 publisher pool 32，单独验证发布端并行度。

### 瓶颈点

publisher pool 翻倍后入口和落库均没有稳定收益，说明发布并行度不是当前瓶颈。继续增加 publisher 只会增加连接和调度成本，链路限制仍主要位于异步消费及 MySQL 批量落库。

入口与落库指标分别发生约 2% 的反向变化，没有形成一致收益，按正常运行波动处理。publisher pool 16 已能覆盖当前 200 HTTP 并发，不保留 32。

下一轮恢复 publisher 16 和 2 个消费者，仅将 batch size 从 100 调为 200、prefetch 从 200 调为 400，以减少事务数并继续保持低消费者争用。

## 2026-08-09：2 消费者与 batch size 200

本轮恢复 publisher pool 16，消费者保持 2，只将 batch size 从 100 调为 200、prefetch 从 200 调为 400。

| 指标 | 2 × 100 基线 | 2 × 200 | 变化 |
| --- | ---: | ---: | ---: |
| HTTP QPS | 1,157.70 | 1,078.96 | -6.8% |
| 两轮基线平均 HTTP QPS | 1,076.34 | 1,078.96 | +0.2% |
| 平均延迟 | 172.15ms | 184.73ms | +7.3% |
| P95 | 235.16ms | 268.44ms | +14.2% |
| P99 | 271.23ms | 325.52ms | +20.0% |
| 核心落库 | 915.58 条/秒 | 980.15 条/秒 | +7.1% |
| 消费批次 | 214 | 116 | -45.8% |
| 平均批次 | 93.46 | 172.41 | +84.5% |
| 最终一致性 | 通过 | 通过 | — |

### 瓶颈点

扩大批次后事务数下降 45.8%，证明此前的主要损耗来自事务固定开销；但单批仍需完成幂等校验和多个业务表写入，落库稳定在约 980 条/秒。此时继续扩大批次会增加聚合等待和失败回退成本，下一步应定位事务耗时、锁等待和慢 SQL，而不是只调大 batch size。

20,000 条核心记录的落库跨度从 21.844 秒缩短到 20.405 秒。HTTP QPS 低于最好的一次基线，但与两轮基线平均值基本一致；核心落库吞吐提高约 7.1%，事务数减少约 45.8%，且没有重试、死信、未认领事件或最终一致性错误。

本轮保留 `publisher pool=16`、`consumer=2`、`prefetch=400`、`batch size=200`、`batch wait=10ms` 作为下一阶段 benchmark 配置。该结论描述为“减少事务并提高核心落库吞吐”，不将单轮波动表述为入口 QPS 提升。

## 2026-08-09：WebSocket 多房间场景

WebSocket benchmark 增加 `--rooms`。`--video-id` 表示连续视频 ID 的起点，客户端按序号轮询分配到房间，所有 publisher 使用全局序号在房间间均匀发布。结果使用 schema v2，除全局指标外还记录逐房间发布数、应收/实收、完整率、重复数、协议错误和 10ms 精度的延迟分位数。

测试仍使用三台 4C8G 主机，被压机运行单个 API 实例并将容器 `nofile` 提高到 65535。正式测量均持续 30 秒，使用独立的 ready preview 视频作为房间。

| 场景 | 房间与连接 | 实际发布 | 广播投递 | 完整率 | P50 | P95 | P99 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 单热点房间基线 | 1 × 1000 | 99.66/s | 99,663/s | 100% | 45ms | 70ms | 78ms |
| 5 个高频房间 | 5 × 200 | 343.42/s | 68,685/s | 100% | 53ms | 270ms | 310ms |
| 1000 个低频房间 | 1000 × 5 | 99.66/s | 498.32/s | 100% | 8ms | 13ms | 18ms |

5 个高频房间共完成 10,303 次发布和 2,060,600 次投递，零发布失败、零重复、零协议错误。每个房间完成约 2,060 次发布，逐房间完整率均为 100%，P99 分布为 310～330ms，没有出现房间饥饿。目标发布速率为 500/s，但同步 MySQL 持久化、Redis 发布和 Hub 广播组成的完整发布链路实际稳定在约 343/s。

1000 个低频房间共维持 5,000 条连接，全部建连成功。每个房间在测量窗口收到 2～3 条消息，1,000 个房间均有有效样本且完整率全部为 100%；逐房间 P99 中位数为 10ms、P95 房间为 20ms、最大为 30ms。API 在测试期间内存约 295MiB，说明大量低频房间的主要成本是长连接状态，而不是广播 CPU。

### 瓶颈点

热点场景受单 Hub 事件循环串行扇出以及同步 MySQL、Redis 发布链路限制；房间内连接越多，单条消息的投递成本越高。大量低频房间当前没有触及广播瓶颈，主要容量约束转为文件描述符、连接状态和内存。

当前单实例 Hub 使用一个事件循环串行处理所有房间的广播。多房间分配保持公平，但热点场景的总吞吐仍受单 Hub 和同步发布链路限制；横向扩展 API 实例、让每个实例只扇出本机连接，比继续增加单 Hub 队列更符合现有 Redis Pub/Sub 架构。

## 瓶颈定位与原因

### 选课链路：入口受理与异步落库是两个独立上限

选课接口成功返回只代表 Redis 原子扣减及消息可靠发布已经完成，MySQL 由消费者异步落库。因此需要分别观察两个上限：

- **入口受理上限约为 1,080～1,160 QPS。** publisher pool 从 16 增加到 32 后，HTTP QPS 反而从 1,157.70 降至 1,130.70，落库吞吐仅有 2.4% 波动，说明当前 200 HTTP 并发下发布池不是主要瓶颈。入口耗时主要来自 Redis 原子操作、RabbitMQ publisher confirm 以及网络往返，继续增加 publisher 数不会线性提高吞吐。
- **异步落库上限约为 980 条/秒。** batch size 从 100 增加到 200 后，平均批次由 93.46 提升到 172.41，消费事务数由 214 降到 116，落库吞吐由 915.58 提升到 980.15 条/秒；与此同时 HTTP QPS 与两轮基线均值基本相同。这说明扩大批次优化的是下游事务效率，不是入口受理能力。
- **持续端到端吞吐取两者较小值。** 如果入口长期以约 1,100 QPS 接收，而落库只能维持约 980 条/秒，短时测试仍会 100% 成功，但 RabbitMQ 中会逐渐形成积压。因此当前单实例完整链路的可持续容量应按约 980 条/秒估算，而不能只引用入口峰值 QPS。

落库的主要成本是每批事务的固定开销和并发事务争用。一个消费批次需要完成幂等事件写入、状态校验以及 application、enrollment、教学班名额等多表更新；批次越碎，SQL 往返和事务提交次数越多。消费者从 2 增加到 4 后，平均批次从 93.46 降到 80，事务数增加 16.8%，并且多个事务会竞争相同教学班及相关记录，最终落库吞吐下降 21.6%。这也是“增加消费者但吞吐下降”的直接原因。

测试中各容器 CPU 均未耗尽 4 核，但这不代表数据库仍有同等比例的吞吐余量：事务可能在等待锁、日志刷盘或网络往返，此时 CPU 不会满载。后续优化应优先记录批事务耗时、锁等待、慢 SQL 和 redo/fsync 指标，再决定是否合并 SQL、补充索引或拆分数据；不应仅凭整机 CPU 余量继续增加消费者。现阶段保留 `2 consumers + batch size 200` 是更合适的配置。

### WebSocket：热点扇出受单 Hub 串行模型限制

WebSocket 链路也包含两个不同指标：HTTP 发布 QPS 表示每秒接受多少条弹幕，广播投递 QPS 表示这些弹幕经过扇出后被所有连接接收的总次数。一次向 1,000 人房间发布的成本约等于 1,000 次连接队列投递，不能把两者直接比较。

- **单热点房间的主要瓶颈是扇出。** 单房间 1,000 条连接、约 100 次发布/秒时，单实例稳定完成约 99,663 次投递/秒，完整率 100%、P99 78ms。Hub 由单个事件循环串行处理注册、注销和广播，每条消息还需要遍历该房间的连接并写入各客户端发送队列，因此扇出成本随房间连接数线性增长。
- **多个热点房间仍共享同一个串行 Hub。** 5 个房间虽然没有饥饿，但目标 500 次发布/秒只达到 343.42 次/秒，P99 上升到 310ms。增加房间不会增加 Hub 并行度，反而增加更多广播事件、房间查找和连接快照等固定成本；任一热点广播变慢也会推迟其他房间，形成跨房间的队头阻塞。
- **过载后先表现为延迟和客户端队列积压。** 此前 2,000 连接、100 次发布/秒的探测共应接收 2,740,000 次、实际接收 2,728,575 次，出现 1,198 次 `client_queue_full`，P99 达 7.85s、最大延迟 16.155s。该组只用于定位过载边界，不作为稳定成绩。每个客户端的发送队列有界；当 Hub 投递速度超过连接 write pump 的排空速度时，继续增大队列只会用更多内存换取更高延迟，不能消除瓶颈。
- **大量低频房间当前不是 CPU 瓶颈。** 1,000 个房间、5,000 条连接仍保持 100% 完整率和 18ms P99，说明房间数量本身的影响较小。此场景首先消耗的是文件描述符、连接状态和内存，API 约占 295MiB；容量规划需要持续观察单连接内存和 `nofile`，而不是只看消息吞吐。

热点场景的优化顺序应是：按 `video_id` 对 Hub 分片，使多个事件循环可以并行扇出；或横向扩展 API，让 Redis Pub/Sub 将消息送到各实例，而每个实例只遍历本机连接。发布接口还同步执行视频状态校验、MySQL 持久化、缓存失效和 Redis 发布，这限制了消息发布 QPS；可进一步缓存可播放状态，并在业务允许时将持久化改为可靠异步写入。扩容或改造后仍应同时报告发布 QPS、投递 QPS、P99 和 `client_queue_full`，防止只提高入口速度却把积压转移到连接队列。
